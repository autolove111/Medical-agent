🧠 MedLabAgent 记忆层架构全景分析

基于 Claude / Hermes / CrewAI / OpenClaw 四大框架的设计理念，结合本项目实际实现，从长、中、短期记忆三维度深度剖析

🏛️ 一、长期记忆（LTM）— 跨会话持久化，四部分架构

长期记忆负责跨会话持久化存储患者所有信息，采用关系数据库为主体，辅以向量检索能力（如 pgvector 扩展）。逻辑上分为四块：

P1

用户画像 跨会话共享 · 每人一条

存储患者一生不变的静态信息，每个患者只有一条记录，每次对话开始时全量加载到短期记忆的工作缓存中。

身份标识(脱敏ID) 年龄 性别 血型 慢性病 手术史 过敏史 长期用药 家族史 生活习惯
-- PostgreSQL: patient_profile 表 patient_id (PK), name, age, gender, blood_type, height, weight, allergies (JSON), chronic_diseases (JSON), medications (JSON), family_history (JSON), lifestyle (JSON)
P2

时间轴快照 事件级 · 按时间存储

最细粒度的长期记忆，记录每次对话中产生的重要事件，每个事件带精确时间戳和所属会话ID。支持时间范围查询和语义相似度检索两种模式。

症状描述 化验单结果 影像检查报告 用药变更 医生诊断与建议 关键摘要快照
-- session_data 表 (event_type = symptom / lab_result / imaging) patient_id, session_id, event_type, content, raw_data (JSON), created_at -- 索引: patient_id + created_at 支持时间范围查询 -- pgvector 扩展支持语义相似度检索
P3

对话历史消息 原始记录 · 有保留策略

从短期记忆"存档"下来的完整对话原文。每条消息标记所属会话ID和轮次编号。设置保留策略控制存储膨胀：

  • 近期（90天内）的消息保留全文
  • 超过90天的消息被删除，但关键信息已在 P2 中以事件形式保留，不会完全丢失
-- session_data 表 (event_type = message) patient_id, session_id, event_type='message', role (user/assistant), turn_id, content -- 保留策略: created_at > 90天 的记录定期清理
P4

会话总结 每个会话一条 · 高层聚合

每个会话结束后，由 LLM 根据完整对话历史和产生的事件生成一份高度精炼的总结（200字左右），包含：

主诉 关键症状变化 医生建议 患者疑问 已执行检查/用药 待跟进事项
-- session_data 表 (event_type = summary) patient_id, session_id, event_type='summary', content='200字总结...' -- 不替代时间轴事件，提供高层视图，快速了解某次就诊概貌

四部分的关系

  • 第一部分是静态基础，所有会话共享。
  • 第二部分是事件流水，按时间线存储所有重要节点。
  • 第三部分是原始素材，必要时可回溯完整对话（但有期限）。
  • 第四部分是会话摘要，是对第三部分和第二部分的高层聚合。

当需要回答"患者上次就诊说了什么"时，优先查看第四部分（会话总结）和第二部分（关键事件）；只有需要还原完整语境时，才去翻阅第三部分。

为什么这样设计？

  • 为什么不永久保存全部对话原文？ 存储成本高，且大部分信息是冗余的。通过时间轴事件和会话总结，已经能保留核心医疗事实。
  • 为什么还要第三部分（原始消息）？ 因为有些时候需要回溯完整语境，比如审核 AI 是否犯错，或者患者对之前某句话有争议。设置 90 天的保留期，既满足短期审计需求，又控制成本。
  • 为什么不直接用向量数据库替代关系数据库？ 向量检索擅长语义匹配，但不擅长精确的时间范围查询、结构化过滤、事务更新。关系数据库（如 PostgreSQL）配合 pgvector 可以同时提供两种能力，简化架构。

⚡ 二、短期记忆（STM）— 当前会话的热数据

短期记忆存在于每个会话的整个生命周期内，存储在内存/缓存中，会话结束即释放（或压缩后写入长期记忆）。包含三个组件：

💬 对话轮次缓冲区

存什么：保留最近 N 轮对话的完整原文（按 token 数量限制，软上限 10K tokens）

用什么存：Redis + Python dict L1 缓存

为什么用 Redis 而不是纯内存 dict：

  • 进程崩溃后可恢复（Redis 持久化 + 24h TTL）
  • 支持跨进程/多服务器共享状态
  • 原生 TTL 自动过期，无需手动清理

为什么还留一个 Python dict：

  • 作为 L1 缓存：同一进程内频繁访问时直接从 dict 读，避免每次 Redis 序列化/反序列化
  • 写入时同时更新 dict + Redis，保证一致性

压缩策略（滑动窗口）：

  • 先入先出队列，超过限制时最早的轮次被压缩
  • 被压缩的消息由 LLM 生成 200-300 字医学摘要
  • 摘要作为系统消息保留在缓冲区头部
  • 原始文本从短期记忆中丢弃，但已归档到长期记忆

📋 状态跟踪器

存什么：结构化的键值对，记录本次问诊的进度

已收集的信息 待确认的信息 中间结论 问诊阶段

工作方式：随着每轮对话动态更新，构建提示时一并提供给 LLM，使其清楚当前处于问诊的哪个阶段。

问诊阶段追踪：

  • greeting → history_taking → symptom_inquiry → examination_suggestion → conclusion
  • 由 LLM 驱动的 StateTrackerEngine 每轮更新状态 JSON

💰 Token 预算分配器

是什么：逻辑组件，位于短期记忆和 LLM 之间，按优先级填充上下文窗口

优先级（从高到低）：

  • P1：系统提示词（角色、规则）— 固定
  • P2：用户当前输入 — 固定
  • P3：从长期记忆中检索到的相关片段（Top-3~5）— 可裁剪
  • P4：短期记忆中的最近几轮对话 — 可裁剪
  • P5：当前会话状态跟踪器 — 可裁剪

超限处理：从最低优先级开始截断或压缩。历史摘要是 P4 的一部分，空间紧张时可进一步压缩或丢弃。

紧急压缩：如果必须保留高优先级内容但已超限，将多轮对话合并成更短摘要，或减少 LTM 召回数量。

为什么短期记忆不直接把所有历史对话都保留？

LLM 的上下文窗口有限（本项目 Qwen2.5-7B 为 32K tokens），而且如果信息量过大，模型容易被噪声干扰。压缩早期对话为摘要，可以在有限空间里保留更长的时间跨度。

🔍 三、长期记忆的检索与融合（RAG）

在每轮对话中，Agent 不会被动等待用户提问全部历史，而是主动根据当前对话状态生成检索查询。

🕐 检索触发时机

  • 用户每次输入后，立即触发
  • 如果状态跟踪器中标记了"需要补充信息"，也会额外生成针对该症状的检索

🔄 查询生成策略

  • 直接使用用户当前输入作为基础查询
  • 从状态跟踪器中提取实体（症状名、药名）作为补充查询
  • 同义词扩展（如"头痛"→"偏头痛""头胀"）

📡 多路召回

  • 向量检索：查询文本向量化，与 P2 事件向量做相似度匹配
  • 结构化检索：含时间范围/事件类型时，通过数据库索引精确过滤
  • 知识图谱（可选）：查询药物-症状-疾病关系

📊 结果重排序

各路召回结果合并后，按以下维度重排序，选取 Top-5 进入上下文：

  • 语义相似度
  • 时间新鲜度（近期事件权重略高）
  • 事件重要性（如"过敏史"比"一般主诉"更重要）

与短期记忆的融合

构造最终 LLM 提示时：先放系统指令和用户输入 → 再放重排序后的长期记忆片段 → 最后放短期记忆中的最近几轮对话。这样设计是因为长期记忆提供事实背景，短期记忆负责连贯性；如果先放短期记忆，LLM 可能会被最近的对话带偏，忽略历史关键信息。

♻️ 四、数据生命周期管理

写入时机

时机操作写入目标

会话结束时 ① 生成会话总结 → P4

③ 更新用户画像 → P1

遗忘机制

  • 时间衰减：超过一定时间（如两年）且访问频次极低的非关键事件，可以从 P2 中删除
  • 强制保留：标记为"重要"的事件（如恶性肿瘤、严重过敏）永不删除
  • 摘要替代：对于普通对话原文（P3），超过保留期后删除，但其关键信息已以事件形式存在于 P2，不会完全丢失

🚀 九、改进建议

对比四大框架的设计理念，结合本项目实际，提出以下改进方向：

🔴 P0：引入 Dreams 式离线整合

问题：当前短→长转化是同步的，会话结束时一次性提取，可能遗漏跨会话模式（如"患者每次都说头晕"）。

改进：借鉴 Claude 的 Dreams 机制，在空闲期对多个会话存档进行跨会话模式识别，自动发现患者就诊规律、症状演变趋势。

对标 Claude 异步后台

🟠 P1：增加记忆衰减与访问增益

问题：当前事件存储是"只增不删"的，长期运行后检索噪声越来越大。

改进：借鉴 Claude 的差分衰减机制，对不同类型事件设置衰减率（症状 7%/天，化验 2%/天），被检索到的记忆获得增益。关键事件（过敏、恶性肿瘤）标记为"永不衰减"。

对标 Claude 用进废退

🔵 P2：增加技能记忆层

问题：当前系统每次遇到类似问题都从零推理，没有"学会"可复用的处理模式。

改进：借鉴 Hermes 的技能记忆机制，当 Agent 成功处理一类问题（如"解读肾功能报告"）后，自动提炼为技能文件，下次遇到类似任务时按需加载。

对标 Hermes 程序性记忆

🟣 P3：CrewAI 式自适应深度召回

问题：当前 RAG 检索固定 Top-K=3，可能漏掉重要但排名靠后的记忆。

改进：借鉴 CrewAI 的自适应召回策略——先浅层检索（Top-5），置信度低于阈值自动扩大范围（Top-20），甚至沿实体关系图谱扩展一跳。

对标 CrewAI 自适应深度

🏗️ 十、持久化方法构想

当前项目已实现 2 张核心表覆盖全部需求，以下是对未来持久化架构的进一步构想：

当前架构（已实现）

-- 2 张表覆盖全部需求 TABLE patient_profile -- P1: 患者画像（每人一条） patient_id (PK), name, age, gender, blood_type, height, weight, allergies (JSON), chronic_diseases (JSON), medications (JSON), family_history (JSON), lifestyle (JSON) TABLE session_data -- P2+P3+P4: 统一会话表 id (auto PK), patient_id (indexed), session_id (indexed), event_type (indexed: message / lab_result / symptom / summary), role, turn_id, content (Text), raw_data (JSON), created_at

构想一：pgvector 扩展 — 向量检索能力

在 session_data 表上增加 embedding 列，利用 PostgreSQL 的 pgvector 扩展实现原生语义检索，无需独立的向量数据库：

-- 在 session_data 上增加向量列 ALTER TABLE session_data ADD COLUMN embedding vector(768); -- 创建 HNSW 索引（高性能近似最近邻） CREATE INDEX idx_session_embedding ON session_data USING hnsw (embedding vector_cosine_ops); -- 语义检索 + 结构化过滤一体化查询 SELECT * FROM session_data WHERE patient_id = 'p001' AND event_type IN ('symptom', 'lab_result') AND created_at > now() - interval '90 days' ORDER BY embedding <=> '[查询向量]'::vector LIMIT 5;

构想二：自动归档与清理策略

-- 定时任务：清理超过 90 天的对话原文（P3） -- 关键信息已在 P2（事件）和 P4（总结）中保留 DELETE FROM session_data WHERE event_type = 'message' AND created_at < now() - interval '90 days'; -- 定时任务：衰减非关键事件（可选） -- 对超过 2 年且未被检索过的普通症状事件归档 UPDATE session_data SET event_type = 'archived_symptom' WHERE event_type = 'symptom' AND created_at < now() - interval '2 years' AND raw_data->>'importance' < '7';

构想三：跨会话模式发现（Dreams 式离线整合）

-- 后台任务：定期分析患者就诊模式 -- 输入：某患者最近 N 个会话的总结（P4）和事件（P2） -- 输出：就诊规律、症状演变趋势、用药效果评估 SELECT session_id, content, created_at FROM session_data WHERE patient_id = 'p001' AND event_type = 'summary' ORDER BY created_at DESC LIMIT 10; -- LLM 分析后生成"患者健康趋势报告" -- 写回 session_data (event_type = 'trend_report')

构想四：冷热数据分层

层级数据存储访问频率
热数据 当前会话的对话 + 状态 Redis (STM) 每轮对话读写
